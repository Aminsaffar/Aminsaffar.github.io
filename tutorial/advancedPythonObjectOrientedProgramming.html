Composition:
A Car Built from Objects

A car is not just one large object containing unrelated variables. It is a system of collaborating objects: an engine performs work, a driver operates the car, and passengers occupy seats.

HAS-A relationshipObject collaborationOwnership & lifecycleDependency injection
01 · The central idea

What is composition?

Composition is an OOP design technique in which an object is built using other objects. Instead of inheriting all behavior from a parent class, the containing object delegates work to its component objects.

CarWhole object
contains →
EngineComponent
DriverComponent
PassengersComponents

Car has an Engine

The engine provides start, stop, and power-related behavior.

Car has a Driver

The driver has identity and can perform driving actions.

Car has Passengers

The car manages a collection of people occupying seats.

Key distinction: A Driver is not a kind of Car. A Passenger is not a kind of Car. They are separate objects that collaborate with a Car.
02 · Start with the wrong design

Why not put everything inside Car?

Imagine writing one enormous class that stores engine details, driver information, passenger records, seat allocation, and every related operation.

Not recommended: one class doing everything
class Car:
    def __init__(self, brand, engine_type, driver_name):
        self.brand = brand
        self.engine_type = engine_type
        self.engine_running = False
        self.driver_name = driver_name
        self.passenger_names = []
        self.fuel_level = 50

    def start_engine(self):
        self.engine_running = True

    def add_passenger(self, name):
        self.passenger_names.append(name)

    def driver_introduces(self):
        print(self.driver_name)

    def refuel(self, amount):
        self.fuel_level += amount

This may work for a tiny example, but the class now has several responsibilities. As the application grows, it becomes harder to test, extend, and maintain.

03 · Build the components

Give every concept its own class

Each class should represent a meaningful concept and own the behavior related to that concept.

Engine class

engine.py
class Engine:
    def __init__(self, engine_type, horsepower):
        self.engine_type = engine_type
        self.horsepower = horsepower
        self.is_running = False

    def start(self):
        if self.is_running:
            print("Engine is already running")
            return

        self.is_running = True
        print("Engine started")

    def stop(self):
        self.is_running = False
        print("Engine stopped")

    def status(self):
        return "Running" if self.is_running else "Stopped"


engine = Engine("Petrol", 150)
engine.start()
print(engine.status())

Driver class

driver.py
class Driver:

04 · Connect the objects

Car contains an Engine, Driver, and Passengers

Now the Car class receives objects and coordinates them. Notice the important difference: self.engine stores an Engine object, not merely an engine-type string.

car_composition.py
class Engine:
    def __init__(self, engine_type):
        self.engine_type = engine_type
        self.is_running = False

    def start(self):
        self.is_running = True
        print(f"{self.engine_type} engine started")

    def stop(self):
        self.is_running = False
        print("Engine stopped")


class Driver:
    def __init__(self, name):
        self.name = name

    def drive(self):
        print(f"{self.name} is driving")


class Passenger:
    def __init__(self, name):
        self.name = name


class Car:
    def __init__(self, brand, engine, driver):
        self.brand = brand
        self.engine = engine
        self.driver = driver
        self.passengers = []

    def add_passenger(self, passenger):
        self.passengers.append(passenger)
        print(f"{passenger.name} entered the car")

    def start(self):
        print(f"Starting {self.brand}")
        self.engine.start()
        self.driver.drive()

    def show_passengers(self):
        print("Passengers:")
        for passenger in self.passengers:
            print(f"- {passenger.name}")


engine = Engine("Petrol")
driver = Driver("Alex")
car = Car("Toyota", engine, driver)

car.add_passenger(Passenger("Sara"))
car.add_passenger(Passenger("John"))

car.start()
car.show_passengers()
Look closely: self.engine = engine stores a reference to an existing Engine object. When self.engine.start() is called, the Car delegates the operation to that component.
05 · Understand the references

Objects are connected by references

Python variables hold references to objects. When you pass an object to a constructor, you generally pass a reference to the same object — you do not automatically make a copy.

reference_identity.py
class Engine:
    pass


class Car:
    def __init__(self, engine):
        self.engine = engine


engine = Engine()
car = Car(engine)

print(car.engine is engine)  # True

engine.custom_note = "Shared object"
print(car.engine.custom_note)

Because both names refer to the same object, a change made through one reference can be observed through the other.

06 · Object relationship types

Composition vs aggregation

Both are forms of object association. The distinction is about ownership and lifecycle, not a special Python keyword.

RelationshipOwnership ideaExampleTypical lifecycle
CompositionStrong whole-part ownershipCar owns its built-in engine componentPart is conceptually tied to the whole
AggregationWeak/shared associationCar has a passengerPassenger exists independently
AssociationObjects know or use each otherDriver operates a carIndependent lifecycles
Important nuance: Python does not enforce composition or aggregation. These are design concepts. A Car can own an Engine, but an Engine object can also exist independently in Python. The relationship is determined by your design and lifecycle rules.

Example: a passenger exists without the car

aggregation.py
class Passenger:
    def __init__(self, name):
        self.name = name


class Car:
    def __init__(self):
        self.passengers = []

    def board(self, passenger):
        self.passengers.append(passenger)


sara = Passenger("Sara")
car = Car()

car.board(sara)

print(car.passengers[0] is sara)
del car

# Sara still exists because another reference points to her.
print(sara.name)

Deleting the variable car does not delete Sara. The passenger has an independent reference and lifecycle.

07 · Who creates the component?

Two ways to construct composed objects

1. Create components inside the whole

internal_creation.py
class Engine:
    def __init__(self, engine_type):
        self.engine_type = engine_type


class Car:
    def __init__(self, brand):
        self.brand = brand
        self.engine = Engine("Electric")


car = Car("Nova")
print(car.engine.engine_type)

This is convenient when the Car is responsible for creating and managing its Engine component.

2. Inject components from outside

dependency_injection.py
class Engine:
    def __init__(self, engine_type):
        self.engine_type = engine_type


class Car:
    def __init__(self, brand, engine):
        self.brand = brand
        self.engine = engine


petrol_engine = Engine("Petrol")
electric_engine = Engine("Electric")

car_a = Car("Roadster", petrol_engine)
car_b = Car("E-Motion", electric_engine)

print(car_a.engine.engine_type)
print(car_b.engine.engine_type)

This is called dependency injection: the Car receives the dependency it needs instead of constructing it internally.

Why inject dependencies? You can swap implementations, reuse existing objects, and pass test doubles during testing. The Car becomes less tightly coupled to one concrete Engine implementation.
08 · A realistic model

Seats, capacity, and passenger management

Let's make the model more realistic. A car has a fixed number of seats. One seat is reserved for the driver, and the remaining seats are available to passengers.

car_seats.py
class Passenger:
    def __init__(self, name):
        self.name = name


class Driver:
    def __init__(self, name):
        self.name = name


class Car:
    def __init__(self, brand, driver, seat_count):
        if seat_count < 1:
            raise ValueError("A car needs at least one seat")

        self.brand = brand
        self.driver = driver
        self.seat_count = seat_count
        self.passengers = []

    @property
    def passenger_capacity(self):
        return self.seat_count - 1

    @property
    def available_passenger_seats(self):
        return self.passenger_capacity - len(self.passengers)

    def add_passenger(self, passenger):
        if self.available_passenger_seats <= 0:
            raise ValueError("No passenger seats available")

        self.passengers.append(passenger)
        print(f"{passenger.name} boarded")

    def show_occupants(self):
        print(f"Driver: {self.driver.name}")
        for passenger in self.passengers:
            print(f"Passenger: {passenger.name}")
        print(f"Seats available: {self.available_passenger_seats}")


car = Car("Toyota", Driver("Alex"), seat_count=5)
car.add_passenger(Passenger("Sara"))
car.add_passenger(Passenger("John"))
car.show_occupants()

Notice that the Car owns the rule for passenger capacity and boarding. Passenger stores passenger-specific data. Driver stores driver-specific data.

09 · Better architecture

Depend on behavior, not a concrete class

Suppose the car should work with different engine types. Rather than checking exact classes everywhere, define the expected behavior and let each engine implement it.

engine_interface.py
from abc import ABC, abstractmethod


class Engine(ABC):
    @abstractmethod
    def start(self):
        pass


class PetrolEngine(Engine):
    def start(self):
        print("Petrol engine started")


class ElectricMotor(Engine):
    def start(self):
        print("Electric motor activated")


class Car:
    def __init__(self, engine):
        self.engine = engine

    def start(self):
        self.engine.start()


petrol_car = Car(PetrolEngine())
electric_car = Car(ElectricMotor())

petrol_car.start()
electric_car.start()

This combines composition, abstraction, and polymorphism:

  • Composition: Car has an engine object.
  • Abstraction: Engine defines the expected operation.
  • Polymorphism: PetrolEngine and ElectricMotor implement that operation differently.
10 · Design checklist

How to decide what should become a class

  1. Identify the concept. Is Engine, Driver, or Passenger a distinct thing in your problem domain?
  2. Identify its own data. Does it have state that belongs naturally to it?
  3. Identify its own behavior. Does it perform operations that should not be implemented by Car?
  4. Define the relationship. Does Car own it, contain it, use it, or merely refer to it?
  5. Choose lifecycle ownership. Can the component exist independently? Can it be shared or replaced?
  6. Define the interface. What operations does Car need from the component?
  7. Delegate behavior. Let the component perform its own responsibility.
Good design question: If the engine implementation changes, should you need to rewrite passenger management? If the answer is no, keeping those responsibilities in separate classes is a good boundary.

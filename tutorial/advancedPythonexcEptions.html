1. What are errors and exceptions?

An exception is an object Python creates when something goes wrong while a program is running. If the exception is not handled, the current operation stops and the program usually terminates with a traceback.

Syntax error

The code cannot be parsed.

if True
    print("Hi")
Runtime exception

The code is valid, but an operation fails at runtime.

result = 10 / 0
Logic error

The program runs but produces the wrong result.

average = total / 2  # Wrong divisor?

Exception handling lets you respond to expected failures instead of allowing them to crash the program.

Key idea: use exceptions for exceptional situations and recoverable failures. Do not use them to hide bugs or replace ordinary control flow unnecessarily.

2. The basic structure and execution flow

try:
    # Code that might raise an exception
    risky_operation()
except SomeException:
    # Recovery or error handling
    handle_problem()

Python executes the try block from top to bottom. If no exception occurs, it skips all matching except blocks. If an exception occurs, Python searches for the first compatible handler.

  1. Run statements inside try.
  2. When an exception occurs, stop executing the remaining statements in that try block.
  3. Find the first matching except.
  4. Run that handler, then continue after the complete try/except structure.
Try it: division with recovery
try:
    number = int("25")
    result = 100 / number
    print(result)
except ValueError:
    print("Please enter a valid integer.")
except ZeroDivisionError:
    print("The number cannot be zero.")

print("Program continues.")

3. Your example, explained line by line

Your code demonstrates three different failures: invalid integer conversion, division by zero, and an operation that is invalid for an integer.

a = input("Please enter a: ")

try:
    a = int(a)
    b = 100 / a
    print(b)
    # a = []
    a[10] = 0
except ValueError as v_error:
    print(v_error)
    print("Invalid value")
except ZeroDivisionError:
    print("a should not be zero")
except Exception as exception:
    print(exception)
    print("An exception happened")

A clearer corrected version

user_input = input("Please enter a: ")

    result = 100 / number
    print(result)

except ValueError as error:

    print("The number must not be zero.")

except TypeError as error:
    print(f"Invalid operation: {error}")

except Exception as error:
    print(f"Unexpected error: {error}")

In this version, the variable names communicate their roles. The broad handler is retained as a final safety net, but expected errors have their own specific handlers.

4. Multiple except blocks and exception variables

You can write several except blocks to handle different failure types. Only the first matching handler runs.

try:
    value = int(input("Number: "))
    print(50 / value)
except ValueError as error:
    print("The input was not an integer:", error)
except ZeroDivisionError:
    print("Cannot divide by zero.")
except TypeError as error:
    print("Wrong data type:", error)

as error assigns the caught exception object to a variable. You can print it, inspect its type, or log it.

except ValueError as error:
    print(type(error).__name__)
    print(str(error))
    print(repr(error))

Handle several exception types together

If the recovery action is identical, group exception classes in a tuple:

try:
    number = int("not a number")
except (ValueError, TypeError) as error:
    print(f"Input conversion failed: {error}")
Order matters: put more specific exception classes before broader parent classes. A broad handler placed first can make later handlers unreachable.

5. else and finally

Python supports two optional clauses in addition to try and except.

else

Runs only if the try block completes without raising an exception.

finally

Runs whether an exception happened or not, typically for cleanup.

try:
    number = int("20")
except ValueError:
    print("Conversion failed.")
else:
    print("Conversion succeeded:", number)
finally:
    print("This message always runs.")

Why use else?

Keep the statements that depend on successful execution in else. This avoids accidentally catching exceptions raised by code that is not part of the operation you intended to protect.

try:
    number = int(user_text)
except ValueError:
    print("Please enter an integer.")
else:
    # This code runs only after successful conversion.
    print(100 / number)

Notice that a ZeroDivisionError in the else block is not caught by the except clauses belonging to that same try statement.

finally for cleanup

file = None
try:
    file = open("notes.txt", "w", encoding="utf-8")
    file.write("Hello")
except OSError as error:
    print("File operation failed:", error)
finally:
    if file is not None:
        file.close()
For files, prefer with open(...). A context manager closes the file automatically, even if an exception occurs.
with open("notes.txt", "w", encoding="utf-8") as file:
    file.write("Hello")

6. Raising exceptions with raise

raise lets your code report that an operation cannot be completed. You should raise a meaningful exception when an input or state violates the function's requirements.

age = -5

if age < 0:
    raise ValueError("Age cannot be negative.")

Validate function arguments

def calculate_discount(price: float, percent: float) -> float:
    """Calculate a discounted price after validating the inputs."""
    if price < 0:
        raise ValueError("Price cannot be negative.")
    if not 0 <= percent <= 100:
        raise ValueError("Percent must be between 0 and 100.")
    return price * (1 - percent / 100)

Re-raise an exception

Inside an except block, bare raise raises the same exception again, preserving its traceback.

try:
    result = 10 / 0
except ZeroDivisionError:
    print("Logging the failure...")
    raise

Use raise SomeException("message") to create a new exception, and bare raise when re-raising the current one.

7. Creating custom exceptions

Custom exceptions make your program's error conditions clear and meaningful. Define them by inheriting from Exception or one of its subclasses.

class InsufficientBalanceError(Exception):
    """Raised when an account lacks the requested funds."""


def withdraw(balance: float, amount: float) -> float:
    """Withdraw money and return the remaining balance."""
    if amount <= 0:
        raise ValueError("Withdrawal amount must be positive.")
    if amount > balance:
        raise InsufficientBalanceError("Not enough money.")
    return balance - amount


try:
    remaining = withdraw(100, 150)
except InsufficientBalanceError as error:
    print(error)

Custom exceptions with extra information

class InvalidProductError(Exception):
    """Raised when a product identifier is invalid."""

    def __init__(self, product_id: int) -> None:
        self.product_id = product_id
        super().__init__(f"Unknown product ID: {product_id}")

Keep custom exception classes focused. In most applications, a descriptive class name and message are enough; add attributes only when callers need structured details.

9. Understanding tracebacks

A traceback is Python's report of the call stack when an exception is unhandled. Read it from the bottom upward:

  • The last line gives the exception type and message.
  • The lines above show the sequence of function calls.
  • The most relevant final frame usually points to the line where the exception was raised.
Traceback (most recent call last):
  File "app.py", line 8, in <module>
    calculate()
  File "app.py", line 4, in calculate
    return 10 / 0
ZeroDivisionError: division by zero

To inspect or log an exception with its traceback:

import logging

try:
    result = 10 / 0
except ZeroDivisionError:
    logging.exception("Could not calculate the result.")

logging.exception() should be called from an exception handler. It includes traceback information automatically.

10. Best practices

Catch specific exceptions

Handle ValueError, OSError, and other expected errors explicitly.

Keep try blocks small

Protect only the statements that can fail in the way you intend to handle.

Do not hide errors

Avoid empty handlers such as except: pass.

Give useful messages

Explain what failed and, when appropriate, how to fix it.

Clean up resources

Prefer context managers such as with open(...).

Do not overuse exceptions

Use normal conditions for ordinary choices and expected branching.

A robust input loop

while True:
    user_text = input("Enter a positive integer: ")

    try:
        number = int(user_text)
        if number <= 0:
            raise ValueError("The number must be positive.")
    except ValueError as error:
        print(f"Invalid input: {error}")
    else:
        print("Accepted:", number)
        break

Exception chaining

When translating a low-level error into a higher-level one, use raise ... from error to preserve the original cause.

def load_configuration(path: str) -> str:
    """Read configuration text and translate file errors."""
    try:
        with open(path, encoding="utf-8") as file:
            return file.read()
    except OSError as error:
        raise RuntimeError("Could not load configuration.") from error

11. Advanced patterns

Exception groups (Python 3.11+)

When concurrent or grouped operations produce several independent failures, Python 3.11 introduced ExceptionGroup and except*.

try:
    raise ExceptionGroup(
        "Several tasks failed",
        [ValueError("bad value"), TypeError("wrong type")]
    )
except* ValueError as group:
    print("Value-related failures:", group)
except* TypeError as group:
    print("Type-related failures:", group)

Assertions are not input validation

assert is intended for debugging assumptions during development. Python can disable assertions with optimization, so do not use them to validate user input or security-sensitive conditions.

assert internal_count >= 0  # Development invariant

if user_age < 0:
    raise ValueError("Age cannot be negative.")

When to use EAFP and LBYL

EAFP means “Easier to Ask Forgiveness than Permission”: try the operation and handle the exception. LBYL means “Look Before You Leap”: check conditions before the operation.

# EAFP
try:
    value = settings["theme"]
except KeyError:
    value = "default"

# LBYL
if "theme" in settings:
    value = settings["theme"]
else:
    value = "default"

Both can be appropriate. Prefer the approach that is clearest and handles race conditions correctly for the situation.
